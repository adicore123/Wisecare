# חיבור טופס המרחב האישי למייל — Apps Script

החיבור מיועד להרשמות מדף `/space`. נשלחות שתי הודעות נפרדות: אישור הרשמה למשתמש והתראה לבעל האתר. הודעת המנהל כוללת שם, טלפון, אימייל, שם משתמש, יעד ותאריך הרשמה בשעון ישראל. למשתמש נשלחים אותם פרטי הרשמה וקישור למרחב. **סיסמאות וטוקנים אינם מועברים ל־Apps Script או למיילים האלה.**

## הדרך הקצרה להפעלה בסביבת העבודה הזאת

1. פתח את `scratch/WiseCare-AppsScript-READY.gs` והעתק **את כל הקובץ** אל `Code.gs` בעורך Apps Script. זו גרסה מקומית שהוכנה עם המפתח הסודי והדומיין; אין להעלות אותה למאגר ציבורי.
2. בגרסה המוכנה המקומית (version 2) המפתח, כתובת המנהל והדומיין כבר מוגדרים ב־`WISECARE_CONFIG`. אין צורך למלא Script Properties או להריץ פונקציית הגדרה כדי שהשליחה תפעל. אפשר להריץ `configureWiseCare` לצורך אישור הרשאת שליחת מייל ובדיקת המכסה; ההרצה הזאת אינה שולחת מייל.
3. בקובץ המוכן מייל המנהל הוא `adithelevy@gmail.com`. כתובת משתמש הבדיקה היא `adi050levy@gmail.com`. לשינוי קבוע בגרסה הזאת יש לערוך את `WISECARE_CONFIG` ולפרוס גרסה חדשה. ההוראות להתקנה ידנית מהמקור ללא סודות מופיעות בנפרד בהמשך.
4. בחר **Deploy → New deployment → Web app**. הגדר **Execute as: Me**, ו־**Who has access: Anyone**. אם ארגון Google Workspace אינו מאפשר גישה כזאת, יש לטפל בהגבלת הארגון לפני חיבור השרת.
5. העתק את כתובת הפריסה המסתיימת ב־`/exec` והעבר אותה לחיבור. לא להשתמש ב־`/dev`.
6. בשרת: להכניס את הכתובת ל־`SPACE_LEADS_APPS_SCRIPT_URL` ב־`.env.local`; המפתח `SPACE_LEADS_WEBHOOK_SECRET` כבר הוכן מקומית ומתאים לקובץ המוכן. לאחר מכן להפעיל מחדש את שרת הפיתוח. בפרודקשן יש להגדיר **את שני המשתנים** אצל ספק האחסון ולפרוס מחדש לפי התהליך של הפרויקט.
7. אחרי חיבור הכתובת, לבצע הרשמה אמיתית אחת ולבדוק שתי תיבות, כולל ספאם. רק אז ניתן לאשר שליחה חיה.

הדומיין שהוגדר בגרסה המוכנה הוא `https://wisecare-rlgv.vercel.app`, לפי `CLIENT_APP_URL` המקומי. אם הדומיין משתנה, עדכן גם את `CLIENT_APP_URL` בשרת וגם את `SITE_URL` ב־Script Properties. קישור ההרשמה במייל מכוון לדומיין הזה, גם כשהטופס נבדק ב־localhost.

לא נדרש Trigger, גיליון או חיבור לתיבת Gmail. אחרי עדכון קוד הסקריפט יש לפרוס **גרסה חדשה** דרך Manage deployments; שמירת הקוד לבדה אינה מעדכנת פריסת `/exec` קיימת.

לזיהוי הפריסה המעודכנת: פתיחת כתובת `/exec` בדפדפן מחזירה JSON עם `version: 2` ו־`configured: true`. אם מתקבלת `version: 1`, הקוד בפריסה החיה טרם עודכן לגרסה המוכנה החדשה.

## התקנה ידנית / שחזור בסביבה אחרת

`Code.gs` שבספרייה הזאת הוא המקור ללא סודות. בהתקנה ידנית מדביקים אותו ומגדירים שלושה Script Properties:

| Script Property | ערך |
| --- | --- |
| `WEBHOOK_SECRET` | מפתח של 16 תווים לפחות, זהה ל־`SPACE_LEADS_WEBHOOK_SECRET` בשרת; בסביבה הזאת הוגדר מפתח אקראי בן 16 ספרות לפי בקשת המשתמש |
| `ADMIN_EMAIL` | `setup()` מגדירה את כתובת המנהל `adithelevy@gmail.com` |
| `SITE_URL` | מקור HTTPS מלא, למשל `https://example.com`, ללא נתיב או לוכסן מסיים |

מריצים `setup()` פעם אחת לאימות התצורה ולהרשאה, ואז פורסים Web app. תבנית ENV ללא סודות נמצאת ב־`.env.example` באותה ספרייה. המשתנים סודיים בצד השרת: **אין להוסיף להם `NEXT_PUBLIC_`.**

## התנהגות השליחה

- שדה המייל חובה בטופס ובשרת. הבקשה ל־Google נשלחת רק לאחר יצירת החשבון ושמירתו.
- השרת בוחר רק את השדות הדרושים, חותם על גוף הבקשה עם HMAC-SHA256 וחותמת זמן. הסקריפט מאמת חתימה, חלון של חמש דקות וכתובת מרחב בדומיין המוגדר.
- יש עד שני ניסיונות מיידיים, עם timeout של 12 שניות לכל ניסיון. סטטוס השליחה נבדק מתוך JSON, ולא רק לפי HTTP 200: Google עשויה להחזיר דף התחברות במקום תשובה תקינה.
- מזהה הרשמה קבוע, Script Lock ורישום נפרד לכל נמען מצמצמים כפילויות בניסיונות חוזרים. הרשומות נשמרות כ־24 שעות ומכילות מזהה, טביעת תוכן ודגלי שליחה בלבד. קיימת מגבלה עקרונית: קריסה בין שליחת מייל לשמירת הדגל עלולה לגרום לכפילות בניסיון חוזר; אין הבטחת exactly-once מול MailApp.
- כשל מייל אינו מבטל את החשבון. הטופס מציג הצלחה בשליחה רק לפי התוצאה שהוחזרה. תוצאת המנהל נפרדת מתוצאת המשתמש, ונשמרת ברשומת הלקוח בשדה `spaceEmailDelivery` יחד עם קוד כשל ושעת ניסיון.
- אין תור רקע או שליחה אוטומטית מאוחרת אחרי שני הניסיונות. כשל מתמשך דורש טיפול ומעקב ברשומת הלקוח; אין להגיש שוב הרשמה רק לצורך שליחת מייל.
- כאשר כתובת Apps Script מוגדרת, לא נשלח בנוסף מייל מהספק הישן להרשמה זו. כל עוד כתובת הפריסה ריקה, המנגנון הקיים נשאר פעיל; התראת המנהל החדשה מתחילה רק אחרי החיבור.
- `MailApp` מאשר שהשליחה התקבלה לביצוע; הוא אינו מספק אישור שהמייל הגיע לתיבת הדואר. יש לבדוק ספאם ולבצע בדיקה אמיתית אחרי הפריסה.

## עיצוב ותאימות

שני המיילים נבנים מאותה מעטפת ממותגת בגווני teal/navy: טבלאות, CSS inline, רקע צבע מלא כגיבוי ל־Outlook, גרסת טקסט, preheader נסתר ורוחב גמיש עד 600px. `lang="he"`, `dir="rtl"`, יישור לימין ו־LTR מבודד לאימייל, לטלפון ולשם המשתמש מונעים היפוך ערכים. אין תלות בגופני רשת, JavaScript, תמונות חיצוניות, Flex או Grid.

תצוגות HTML עם נתוני דוגמה בלבד נוצרות ב־`output/space-emails/user.html` ו־`admin.html` באמצעות:

```powershell
node scripts/test-space-lead-email.cjs --preview
```

תצוגת דפדפן אינה מחליפה בדיקת Gmail ו־Outlook אמיתית אחרי פריסה.

## בדיקות מקומיות

```powershell
node --test scripts/test-space-lead-email.cjs
npx tsc --noEmit --pretty false
```

הבדיקות מדמות את שירותי Google ואת ה־fetch של השרת. הן אינן יוצרות חשבונות ואינן שולחות הודעות אמיתיות.
